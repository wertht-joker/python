# 简历打分助手（知识图谱 + LLM）

把简历解析成实体（技能/学校/公司/学历/证书），在**预置的「岗位—技能」知识图谱**里做关系匹配，输出**分维度打分 + 针对性改进建议**，模拟 HR 筛选简历。

> 核心思路：打分走「规则 + 图谱关系」（可解释、非黑盒），LLM 只负责把缺失技能转成个性化建议。

## 功能特性

- 简历解析：PDF / Word / 文本，自动提取技能、学校、学历、公司、证书
- 知识图谱：岗位 ↔ 技能 关系建模，Neo4j 存储，Cypher 查询
- 分维度打分：技能匹配 / 学历背景 / 项目经验 / 实习经历 / 证书，加权汇总总分
- 可解释：每个分数都能回推到「命中了哪个节点 / 缺了哪个技能」
- AI 建议：DeepSeek 基于缺失技能生成针对性改进建议

## 技术栈

| 组件 | 选型 |
|---|---|
| 后端 | FastAPI + Python 3.13 |
| 图数据库 | Neo4j 5（Docker） |
| 简历解析 | PyMuPDF（PDF）+ python-docx（Word） |
| 实体抽取 | 词典 + 规则匹配（确定性，零幻觉） |
| 打分引擎 | 规则 + 图谱关系（非黑盒） |
| 建议生成 | DeepSeek（deepseek-chat） |
| 前端 | Vue3 + Element Plus + ECharts 雷达图 |

## 知识图谱设计

**节点**：`Job`（岗位）、`Skill`（技能，含类别/权重）、`School`（学校，含梯队）、`Company`（公司，含梯队）、`Certificate`（证书，含分值）

**关系**：`(Job)-[:REQUIRES {weight: 核心|重要|加分}]->(Skill)` —— 打分核心；`(Skill)-[:RELATED_TO]->(Skill)` —— 技能等价

预置 19 个岗位（后端×4 / 客户端×2 / 前端 / 算法 / 数据分析 / 测试 / 运维 / 爬虫 / AI Agent / 大数据 / 数据库 / 安全 / 嵌入式 / 游戏 / 区块链）、180+ 技能、学校梯队名单、公司梯队名单、常见证书。

## 启动步骤

### 1. 启动 Neo4j

```bash
docker compose up -d
# 浏览器可视化：http://localhost:7474（免密）
```

### 2. 安装依赖 + 配置

```bash
cd backend
python -m venv venv
venv\Scripts\activate            # Windows
pip install -r requirements.txt
copy .env.example .env           # 填入 DeepSeek Key（建议生成功能需要，不打分也能跑）
```

### 3. 启动后端

```bash
uvicorn app.main:app --reload --port 8001
```

启动时自动建约束并导入预置图谱（幂等，重复启动不产生重复数据）。

### 4. 启动前端

```bash
cd frontend
npm install
npm run dev                     # http://localhost:5174
```

## 打分维度（可解释）

| 维度 | 权重 | 算法 |
|---|---|---|
| 技能匹配 | 40% | Σ命中技能权重 / Σ岗位总权重 × 100（核心=1.0 / 重要=0.6 / 加分=0.3） |
| 学历背景 | 20% | 学校梯队（0~50）+ 学历（0~50） |
| 项目经验 | 20% | 项目数量（0~50）+ 技术覆盖度（0~50） |
| 实习经历 | 15% | 实习公司梯队（大厂100 / 独角兽85 / 中厂70 / 小厂50） |
| 证书加分 | 5% | 命中证书分值累加封顶 |

## 面试高频问题

**Q1：为什么用知识图谱做简历打分？**
简历打分本质是「把简历里的实体（技能/学校/公司）和岗位要求做匹配」。用图建模后，「岗位要求什么技能」就是 `(Job)-[:REQUIRES]->(Skill)` 的图遍历，多跳、带权重、可扩展（加 JD 节点、加技能上下位关系都只加节点边，不改代码）。

**Q2：知识图谱怎么建模的？为什么权重放关系上不放节点上？**
节点：Job / Skill / School / Company / Certificate。技能权重（核心/重要/加分）放 `REQUIRES` 关系的属性上，因为「同一个技能对不同岗位重要性不同」——比如 Java 对 Java 岗是核心、对算法岗是加分，放关系上才正确，放技能节点上就写死了。

**Q3：为什么用 Neo4j 不用 MySQL？**
简历匹配要频繁做「岗位→技能→是否命中」的图遍历和关系查询，Neo4j 原生支持，Cypher 一行搞定，还有浏览器可视化。关系库里要做多表 join，schema 一扩展（加关系类型）就要改表结构，图数据库加关系零成本。

**Q4：实体抽取怎么做？为什么不用 LLM 抽取？**
用「词典 + 规则」：技能/学校/公司都有确定词表，简历文本命中即识别。技能名做了别名归一化（K8s→Kubernetes、SpringBoot→Spring Boot）。不用 LLM 的原因：① 确定性、可复现，同份简历永远同分；② 零幻觉、零成本、零延迟；③ 可解释——每个命中都能定位到原文。LLM 抽取适合开放域，简历这种封闭域词典覆盖率高。

**Q5：打分为什么可解释？**
因为不打黑盒分：技能维度就是「Σ命中权重/Σ总权重」的明确公式，学历维度是「学校梯队分+学历分」的查表，每个分数都能回推到具体命中/缺失了哪个技能节点。面试官问「为什么打 87 分」，能逐项拆解。

**Q6：LLM 在这个项目里扮演什么角色？边界怎么划？**
LLM **不参与打分**，只负责「建议生成」：把「缺失技能 + 各维度分」拼进 prompt，让 DeepSeek 产出自然、个性化的改进建议。这么划边界是因为：打分要稳定可复现（规则做），建议要自然通顺（LLM 做）。用 LLM 打分会不可复现、有幻觉，是常见错误设计。

**Q7：技能匹配怎么处理同义词/别名？**
两层：① 抽取阶段做别名归一化（`SKILL_ALIASES`：K8s→Kubernetes、SpringBoot→Spring Boot、MyBatisPlus→MyBatis-Plus）；② 图谱里用 `RELATED_TO` 关系标注技能等价（Spring↔Spring Boot、NLP↔自然语言处理），后续可做「命中相关技能算部分分」。

**Q8：技能匹配会误判吗？怎么避免？**
英文技能用字母边界正则（`(?<![A-Za-z])Java(?![A-Za-z])`），避免「Java」误命中「JavaScript」；命中「C++」时去掉误命中的「C」；纯中文技能直接包含匹配。当前是精确匹配，更进一步的模糊匹配（技能上下位）可扩展。

**Q9：知识图谱数据从哪来？怎么扩展？**
预置数据（`kg/seed_data.py`）是手工整理的岗位-技能要求 + 学校/公司梯队。扩展方式：① 加新岗位/技能就是往 dict 加一条，`MERGE` 幂等导入；② 接 ownthink 等公开中文知识图谱补充实体；③ 生产环境可从招聘网站 JD 用 LLM 批量抽取岗位要求入库。

**Q10：这个项目还能怎么改进？**
① 简历解析接入 LLM 做更精确的段落切分（教育经历/项目经历/工作经历分块）；② 技能上下位关系（会 Spring Boot 算会 Spring 的 80%）；③ 结合具体 JD 做岗位匹配度打分；④ 学校/公司数据接入完整库（当前是代表性子集）；⑤ 打分权重可配置、支持行业模板。

### 模块专项（按项目涉及的每个模块）

**Q11：简历 PDF / Word 是怎么解析的？**
PDF 用 PyMuPDF（`fitz`）逐页 `get_text()` 提取；Word 用 python-docx 读段落 + 遍历表格（简历常用表格排版，光读段落会漏内容）；txt/md 直接按 UTF-8 读。解析层（`extract/parser.py`）只负责「文件 → 纯文本」，不碰业务逻辑。

**Q12：打分权重（40/20/20/15/5）是怎么定的？**
技能匹配占最大权重（40%），因为技术岗招聘最看重技能对口；学历、项目次之；证书权重最小。权重是**可配置的业务假设**（`config.py` 里 `w_skill` 等），放在配置里而不是写死在代码，不同行业/岗位可换模板。面试强调：权重不是拍脑袋，是可调参数。

**Q13：技能匹配分具体怎么算？举个例子。**
岗位技能分三档权重：核心 1.0 / 重要 0.6 / 加分 0.3。分数 = Σ(命中技能权重) ÷ Σ(岗位全部技能权重) × 100。例：某岗位核心 6 项 + 重要 10 项 + 加分 6 项，总权重 = 6×1.0 + 10×0.6 + 6×0.3 = 13.8；简历命中 4 项核心 + 5 项重要，命中权重 = 4×1.0 + 5×0.6 = 7.0；得分 = 7.0 ÷ 13.8 × 100 ≈ 51。所以缺「核心」技能会显著拉低分——这是刻意设计，让关键技能缺失能被感知。

**Q14：Neo4j 数据怎么导入的？怎么保证重复启动不产生重复数据？**
用 `MERGE` 幂等导入：`MERGE (s:Skill {name: $name})` 存在则复用、不存在才创建；配合 `name` 字段的唯一约束（`CREATE CONSTRAINT ... IS UNIQUE`），即使并发也不会重复。批量用 `UNWIND` 一次传多行。启动时在 lifespan 里先建约束（IF NOT EXISTS）再 seed，所以重启多少次数据都一致。

**Q15：查岗位要求技能用哪条 Cypher？**
`MATCH (j:Job {name: $job})-[r:REQUIRES]->(s:Skill) RETURN s.name AS skill, r.weight AS weight`。从岗位节点出发，沿 `REQUIRES` 边拿到全部技能及权重，打分时再和简历命中的技能求交集。这条查询是整个打分的核心图操作。

**Q16：FastAPI 文件上传怎么处理的？简历文件存不存盘？**
用 `UploadFile`（依赖 python-multipart）。上传后 `tempfile.NamedTemporaryFile` 写到临时文件，解析完 `os.unlink` 立即删除——**不持久化**，因为简历是敏感数据，用后即焚。文件类型按扩展名校验（pdf/docx/txt/md），不支持的直接返回 400。

**Q17：这个项目里 FastAPI 的类型注解和 Pydantic 起了什么作用？**
`GradeRequest` 用 Pydantic 定义 `resume_text`/`job` 字段，FastAPI 自动做请求体校验（字段缺失/类型错误直接 422），并生成 OpenAPI 文档（`/docs` 可交互调试）。打分接口本身是同步函数（Neo4j 驱动同步），但框架支持异步，将来接异步 IO 不用重构。

**Q18：技能别名归一化怎么实现的？为什么归一化而不是建同义词表？**
`SKILL_ALIASES` 字典把常见写法映射到标准名（K8s→Kubernetes、SpringBoot→Spring Boot、MyBatisPlus→MyBatis-Plus），抽取前先 `re.sub` 统一替换。归一化的好处：一次替换后，后面的匹配、打分、展示全用标准名，不用到处处理变体。同义词表更灵活但要额外查表和维护，简历这种封闭域归一化更直接。

**Q19：项目怎么分层的？为什么这么分？**
`kg`（图谱存取）/ `extract`（解析 + 抽取）/ `scoring`（打分 + 建议）/ `api`（路由）/ `schemas`（模型）。分层让「图谱怎么存」「实体怎么抽」「分数怎么算」三者解耦：换图数据库只改 `kg`，换抽取方式只改 `extract`，打分逻辑不动。这是可维护性，也是面试能讲「架构设计」的基础。

**Q20：前端雷达图怎么展示打分结果？**
后端返回 5 个维度的分数，前端用 ECharts 的 `radar` 图，5 个指标（技能/学历/项目/实习/证书）`max=100`，`setOption` 渲染。雷达图能一眼看出「哪个维度是短板」（比数字表直观），命中/缺失技能再用 tag 标签分组展示，缺失的核心技能标红。

**Q21：这个项目和你的 RAG 知识库项目有什么技术关联和区别？**
关联：都用了 FastAPI、DeepSeek、PyMuPDF/python-docx 解析、统一返回结构、Vue3 前端——复用同一套工程范式。区别：知识库是「检索 + 生成」（向量召回 + LLM），核心是 RAG 链路；这个是「抽取 + 图谱匹配」（结构化关系 + 规则打分），核心是知识图谱和可解释性。两者互补，共同体现「AI + 数据工程」的复合能力。
